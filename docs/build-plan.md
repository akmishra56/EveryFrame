# EveryFrame — Build Plan

Supersedes the earlier single-user plan. Read alongside `docs/architecture.md` for the diagrams and data model this plan implements. The original docs (`everyframe-claude-code-kickoff-prompt.md`, `everyframe-handout-brief.md`) still govern everything except "no auth/multi-user" — see `architecture.md` §0 for what changed and why.

## Build order

1. **Scaffolding.** `git init`; npm workspaces (`packages/server`, `packages/web`); base `tsconfig.json` per package; `.gitignore` for `node_modules`, `captures/`, `data/*.db`.

2. **Backend skeleton + CDP connection.** Fastify app. `GET /api/cdp/targets` connects via `connectOverCDP` and lists open pages. Verify against a real Chrome instance (`--remote-debugging-port=9222`) before anything else — this is the one thing that must work against the real world early.

3. **Auth & session foundation.** `User` table; `AuthService` (argon2 password hashing); `SessionManager` on `@fastify/session` + `@fastify/cookie`, backed by a SQLite session store; `POST /api/auth/login`, `POST /api/auth/logout`; `@fastify/rate-limit` on `/api/auth/*`. No MFA yet — get plain login working and tested first.

4. **MFA.** `MfaService` (`otplib` for TOTP, `qrcode` for enrollment QR); `mfa_recovery_code` table; endpoints: enroll (returns secret + QR), confirm (verifies first code, flips `mfa_enabled`), verify (login-time check), disable. The enrollment QR encodes a standard `otpauth://totp/...` URI — works with Google Authenticator, Microsoft Authenticator, or any RFC 6238 app, no per-app branching needed. Wire into the login flow from step 3: `POST /api/auth/login` returns `{mfaRequired: true}` instead of a session when the account has MFA on; `POST /api/auth/mfa` completes it.

5. **Multi-user config storage.** `Config` and `CaptureLog` tables, both scoped by `user_id` (see ERD in `architecture.md` §5). CRUD endpoints (`GET/PUT /api/config`) read/write only the authenticated session's own row — no user ever sees another's config or history. `StorageSettings`, `DisclaimerAcceptance`, and `ActivityLog` tables created here too (empty until later steps use them). `ConfigService.upsert()` writes an `ActivityLog` row (`category: schedule_change`) on every successful save, from this step onward.

6. **Capture + naming.** `Namer.sanitize()` / `Namer.formatDate()` / `Namer.formatTime()` / `Namer.formatTimestamp()`, unit-tested first (exact output contract: `<tabname>_<YYYY_MM_DD_HH_MM_SS>.png`). `CaptureService` writes to `captures/<user_id>/<sanitized-name>_<timestamp>.png`.

7. **Telegram delivery.** `TelegramClient.sendPhoto()` via raw `fetch`, now including a `caption` built by `CaptionRenderer.render(config.caption_template, config.caption_label, now)` — default template `"{label} generated at {time} on {date}"`, reusing `Namer.formatDate`/`formatTime` so the caption's date/time formatting stays consistent with the filename's. `POST /api/telegram/test` sends a real test caption too. Redact the token everywhere it could leak (logs, error responses, DB dumps — encrypted at rest per `architecture.md` §5). Never persist the caption text or the image bytes in `CaptureLog` — only the filename (see `architecture.md` §5); the caption is reconstructible later from `captured_at` + the `Config` row.

8. **Scheduler with full schedule logic.** `SchedulerService.start(userId)` / `.stop(userId)`, one `setInterval` per active user job. Each tick runs the check sequence in `architecture.md` §7.2: schedule date range → active weekday → active time window → interval elapsed → capture → send → retry-once-on-failure → log. A tick outside the window/day/date-range is a no-op, not a stopped job (see state diagram §8.2 — job stays "Running" logically, ticks just skip). Endpoints: `POST /api/capture/start`, `POST /api/capture/stop`, `GET /api/capture/status`, `WS /ws/log`.

9. **Storage & archiving.** `ArchiveService.checkThreshold(userId)` runs after each successful capture (per §7.2); `runArchive()` moves oldest captures to the user's configured `archive_path` until under `threshold_mb`, logs an `ArchiveEvent` row. Endpoints: `GET/PUT /api/storage/settings`, `POST /api/storage/archive` (manual trigger), `GET /api/storage/history`.

10. **Activity & error logging.** `ActivityLogService` (`logError`, `logScheduleChange`, `listForUser`) per `architecture.md` §2a/§10. Wire it into every service that can fail outside a single capture attempt — `CdpTargetService` (Chrome connection lost), `ArchiveService` (archive move failure), `SchedulerService` (job-level failures) — each writing a sanitized one-line summary, never a raw stack trace or secret; the full exception still goes through Pino server-side. `GET /api/logs` merges `ActivityLog` + `CaptureLog` for the authenticated user, newest first, filterable by category (`error` / `telegram_send` / `schedule_change`).

11. **Disclaimer & onboarding nudge.** Frontend: disclaimer modal shown on every successful login (before the main screen renders); "Agree" calls `POST /api/disclaimer/accept`, which writes a `DisclaimerAcceptance` row, then unblocks the UI. Onboarding nudge: shown when the authenticated user has no `Config` row yet; dismissible; disappears permanently once they start their first capture.

12. **Frontend.** Full-screen app shell (no fixed max-width), top app bar with user menu (Profile / Storage / Logs / Log out), matching the published design canvas. React Router with `Login` and the main capture screen loaded eagerly; `Settings` (with its Profile / Security / Logs tabs) and `Storage` loaded via `React.lazy` + `Suspense`. Settings → Logs renders the merged, filterable `GET /api/logs` result as chip-coded rows (see `architecture.md` §10). Wire everything to the real backend from steps 3–11 — no mock/demo data once the backend is live.

13. **End-to-end pass.** Real Chrome (debug port on), a real tab, a real Telegram bot+channel, **two separate user accounts**: confirm each account's config/schedule/capture history stays isolated from the other's; confirm MFA login works end to end; confirm the disclaimer appears on every login and the nudge appears/disappears correctly; confirm a forced-low storage threshold actually triggers an archive move; confirm Settings → Logs shows a real error (e.g. stop Chrome mid-run), a real Telegram send, and a real schedule change, each correctly categorized. This is the definition of done.

14. **Failure alerting & auto-pause (post-v1.0).** Added after comparing EveryFrame against similar open-source projects (`changedetection.io` and smaller Telegram screenshot bots): those alert the user out-of-band when a scheduled job keeps failing, which EveryFrame's original scope didn't — a dead tab or bad token just accumulated silent `failed` rows in Settings → Logs. `Config.failure_alert_threshold` (default 3, 0 disables) now counts consecutive failed ticks in `SchedulerService`; on hitting it, the job stops itself, logs an `ACTIVITY_LOG` entry, and sends one plain-text Telegram alert via a new `TelegramClient.sendMessage()` (same bot/channel already configured). `CaptureStatus` gained `paused`/`pauseReason`; the UI surfaces a distinct "Paused — needs attention" state and a reason banner, with a "consecutive failures" field alongside the other Telegram settings. Calling start() again (the existing "Start capturing" button) clears the pause and resumes normally. See `architecture.md` §7.2, §8.2, §11.

## Verification

- Step 2: manual check against a real running Chrome.
- Step 3: login/logout round-trip; a wrong password is rejected; rate limiting kicks in after repeated failures.
- Step 4: enroll → scan (or manually enter secret) → confirm code → login now requires MFA; a wrong code is rejected; a recovery code works once and then can't be reused.
- Step 5: two accounts, each with their own Config, never see each other's data via the API (not just hidden in the UI).
- Step 6: `namer.test.ts` covers sanitization + timestamp edge cases before step 7 starts.
- Step 7: a real test-send shows the rendered caption (correct label/time/date substitution) in the Telegram channel; confirm `CaptureLog` rows contain no image bytes and no caption text, only the filename.
- Step 8: force a job to fire outside its configured window/day/date-range and confirm it's skipped and logged as nothing (not as a failure); force one inside and confirm the full capture→send→log cycle.
- Step 9: set a low `threshold_mb`, run a capture past it, confirm files actually move to `archive_path` and an `ArchiveEvent` row is written.
- Step 10: force a real error (e.g. kill Chrome mid-capture) and confirm a sanitized summary appears via `GET /api/logs` with no stack trace or secret in the response body; confirm a schedule save produces a `schedule_change` row.
- Step 13: full manual walkthrough per the scenario above.
- Step 14: unit-tested with fake timers and mocked capture/delivery (`schedulerService.test.ts`) — consecutive capture failures trigger exactly one alert and a stop at the configured threshold; a successful tick resets the count; `threshold: 0` disables the behavior entirely; calling `start()` again after a pause clears it and resumes.
- Step 15: verified live end-to-end with a real TOTP code computed from the enrollment secret (not mocked) — create account → land on the MFA offer step → enroll → recovery codes shown → land on the capture screen → log out → log back in and confirm the account now correctly demands the just-enrolled 2FA code.

15. **Signup flow (post-v1.0).** `register` and the MFA enroll/confirm/recovery-code endpoints already existed (steps 3–4) but had no UI path to reach them together — `Login.tsx` only ever rendered a sign-in form. Added a "Create an account" mode to the same page: email/password/display-name → `POST /api/auth/register` → immediate `POST /api/auth/login` (register doesn't itself start a session) → an optional, skippable MFA-setup step reusing the exact enroll/confirm contract from Settings → Security. No new backend routes. The QR/secret/recovery-code CSS moved from `settings.css` (page-scoped, lazy-loaded) into the global `theme.css` so the eagerly-loaded Login page can render the same enrollment UI without importing a lazy page's stylesheet.

16. **Local HTTPS (post-v1.0).** Frontend dev server now serves `https://localhost:5173` via `@vitejs/plugin-basic-ssl` (auto-generated, cached self-signed cert) - the browser only ever talks to this origin, which proxies `/api`/`/ws` to the backend server-side. The backend can optionally serve https too (`EVERYFRAME_HTTPS=true` + `npm run generate-cert -w packages/server`, loaded via a new `loadHttpsOptions()` in `app.ts`, opt-in and disabled under `NODE_ENV=test` so it can't affect `buildApp()` calls in tests). Along the way, fixed a real bug: nothing in the codebase ever actually loaded `packages/server/.env` (no `dotenv`, no `--env-file`) - every `.env` value silently had no effect, masked by the fact that every var read from it also had a safe in-code default. Fixed by adding Node's native `--env-file-if-exists=.env` flag to the `dev`/`start` scripts (the `-if-exists` variant so a missing `.env` still starts cleanly, matching prior behavior).

## Explicitly still out of scope

Multiple tab→channel pairs per user, native desktop packaging, retry backoff beyond one immediate retry, Redis/Postgres/cron infra, per-user Chrome instances / remote machines (see `architecture.md` §1), per-user timezones.
